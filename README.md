# 2DRoundServer

Go backend for the restored 2DRound client (Cocos2d-x Lua, One Piece themed).
It is an independent implementation: the wire protocol was **recovered from a
decompiled client and checked on a real device**, not taken from the original
server, whose source we do not have. Do not describe this as the original
server code.

## Layout
- `cmd/gateway` game TCP gateway (one process per server / `srv_id`)
- `cmd/admin` management HTTP API (admin login, RBAC, servers, accounts, roles, notices, mail, audit), see `docs/ADMIN_API.md`; it also serves the web UI at `/` (`docs/ADMIN_WEB.md`)
- `cmd/loginhttp` HTTP side of login: `url_config.lua`, server list, platform login/register, token
- `internal/proto` frames and field codec driven by `protocols.json` (exported from the client's `proto_mate.lua`)
- `internal/gateway` transport, sessions, router, online hub, 1197 signature check
- `internal/game` command handlers (login sequence only)
- `internal/store` SQLite (modernc, no cgo) and embedded migrations
- `tools/` scripts that patch the restored client to talk to a local machine
- `testdata/captures/` device captures used as replay tests, each with `NOTES.md`

## Run
```sh
go test -race ./...
node --test internal/admin/webtest/lib.test.mjs   # the web UI's pure logic
go run ./cmd/loginhttp -config configs/dev.yaml   # :8081
go run ./cmd/gateway   -config configs/dev.yaml   # :8800 (+ loopback control endpoint :8801)
go run ./cmd/admin     -config configs/dev.yaml   # :8080, prints the first admin password once
```
`go run ./cmd/pcapdecode -in session.pcapng` reads a packet capture of the original game (pcap or pcapng, e.g. from the Android app PCAPdroid) and prints every game frame decoded with the server's field tables as JSON lines; it only reads the file (`docs/CAPTURE_GUIDE.md` says what to capture). A scripted client, `go run ./cmd/bot -user <name>` (against a running `loginhttp` and `gateway`), plays the main line over the real wire (login, create role, hero list, formation, three campaign fights, hook income, quests, achievements, summon state, ranking) and prints one line per step; it exits 1 when a step fails. It checks the real processes, configuration and database without a phone (it caught nothing yet, but the unit tests never start the binaries).
Or start all three in one terminal with `make dev` (`go run ./cmd/devall`; output is prefixed per service, Ctrl+C stops all). `make test` runs vet, the web tests and `go test -race`.
All of them share the SQLite file from `db_path`. Real-device steps and the client
patching tools are described in `testdata/captures/*/NOTES.md` and the docstrings
in `tools/`.

Friend gifts (13316 one friend, 13317 several; the "友情点" gifts): `code` 0 sends a gift to a friend, `code` 1 draws the one a friend sent. From the client's own text: a role may send 10 gifts and draw 30 a day, past the draw limit a draw gives only coin, and sending gives the sender coin. Ours: one gift per friend per day, a gift can only be drawn on the day it was sent, a gift sent is worth 10 friend points to its receiver (`friendPointsEach`), and sending (or a draw past the limit) pays 1000 coin (`coinEach`); the client has no numbers for these. `present_count` in 13300/13316 is how many gifts may still be sent today (the client treats 0 as the limit), `draw_count` how many were drawn today, `draw_all` 30; each friend entry carries `is_present` (already sent today) and `is_draw` (a gift waits). A receiver that is online is told with a 13302. Days are China-time calendar days, like the other daily features. Verified on a device (send, then draw as the other account): see `device-session-2026-10-19/NOTES.md`.

Chat (tests only, not yet on a device): private chat (12720; the recipient gets 12721 with flag 2 showing the sender, the sender an echo with flag 1 showing the recipient; the content flag `len` is passed through) works with any role on the server, friends or not. A role that is offline gets its messages (at most 50 are kept) as one 12722 after the main city is up (after 10304, because the client drops it before it has a role object); they are handed over once and deleted, and 12723 (read) needs no answer. The world channel (12762, channel 1) is pushed to everybody online as 12761, the sender included, and the last 50 are kept in memory for 12766. Other channels (guild, scene, team, cross-server), voice (12725/12726) and the @ notices are not implemented; a message to them is refused with "该频道暂未开放". The channel message's `sign` (md5 of rid, srv_id, channel, len, msg and "____") is checked and a mismatch only logged, like the 1197 signature.

Online gifts (10926 progress, 10927 claim; verified on a device, where the client was seen to send the step's number, 1-12, as `time` in 10927, while the reply and 10926 use the step's seconds): the client's 12 steps (`internal/game/data/online_gifts.json`, `tools/extract_online_gifts.py`; from 60 s to 4 h, each paying a currency or an item) are claimed once per day when the day's online seconds reach the step. The server counts the seconds itself, per calendar day in China time (our policy: the original rule is unknown): a day starts again from 0 at midnight, time while offline does not count, and a login that replaces another keeps what was earned. The reward goes into the same ledgers as mail and selling (a currency id into the asset ledger, anything else into the item ledger), after which 10302 and 10500 are re-sent.

Daily sign-in (14100 state, 14101 sign in; tests only, not yet on a device): the n-th sign-in of a month pays the n-th reward of that month's table (`internal/game/data/checkin.json`, `tools/extract_checkin.py`, 12 months, 366 days), on whichever days the player signs in; a new month starts again from 1; once a day. Invite codes (19800 own code, 19801 enter a code, 19802 invited list with the 19803 push, 19804 progress, 19805 claim; tests only, not yet on a device): every role gets a six-digit code (`invite_codes`); a role enters one code, once (`invite_binds`), and only the first role of its account may (the client text says "only a first-created account"), never a code of its own account, and one code takes at most 20 roles (`bind_num`). The reward steps are the client's 14 (`internal/game/data/invite_tasks.json`, `tools/extract_invite_tasks.py`): each asks that invited roles reach a power or a VIP level and can be claimed once per invited role that did, up to 20 times. The return rewards (19811/19812) and 19807 are not implemented.

Log files: with `log_dir` set (e.g. `data/logs`), every service also writes `<log_dir>/gateway.log`, `loginhttp.log` and `admin.log` (the terminal still gets the same lines), rolls a file over at `log_max_mb` megabytes (default 20; a line is never split) and keeps the newest `log_keep` rolled files as `.log.1`, `.log.2`, ... (default 5). The files are mode 0600 in a 0700 directory, because the logs name accounts and addresses. Without `log_dir` nothing is written to disk. An unusable `log_dir` stops the service at start rather than losing the logs silently.

Config self-check (`config.Check`, printed by the gateway at start as `config: ERROR ...` or `config: warning ...`; nothing stops, a development setup may ignore it): a server list address nobody can reach (empty or 0.0.0.0), a LAN address in the server list or in `login_http.public_base` while the matching service listens on loopback only, a server list port that differs from the gateway's, a `public_base` that is not a URL, the unauthenticated gateway control endpoint (`gateway.admin_addr`) reachable from the network (an error), the admin API reachable from the network over plain HTTP, `login_timeout_seconds` longer than `idle_seconds`, automatic backups off, and `codec.confirmed: false`. These are the mistakes that cost the most time while getting the phone onto the LAN.

Backups: the admin service copies the live database (SQLite `VACUUM INTO`, no downtime) into `admin.backup_dir` (default `backups` next to the database file) when the newest copy is older than `admin.backup_every_hours` (default 24, 0 = off; checked at start and every minute), keeps the newest `admin.backup_keep` (default 14) and checks each copy with `integrity_check`; files are mode 0600 (they hold every account). A superadmin can also make one at once (`POST /api/backups`). To restore: stop the services, copy a backup over `db_path` (and delete its `-wal` / `-shm` files), start again; the migrations run on start. Restoring was rehearsed on a copy of the real database: the counts of accounts, roles, servers and mails matched.

Broadcast (admin Overview page or `POST /api/broadcast`, verified on a device): a message scrolls across the top of every online player's screen (12761 on the NoticeTop channel, 1 to 100 characters, not kept in the chat history). Offline players do not see it.

Connection limits (gateway, tests only for the limits themselves): a connection that has not logged in (no account on its session) is dropped after `gateway.login_timeout_seconds` (default 20, never longer than `idle_seconds`), and one client address may hold at most `gateway.max_conns_per_ip` connections (default 50, 0 = no cap; a phone behind the same router counts as one address, and everything coming through `adb reverse` counts as 127.0.0.1). A refused or timed-out connection is just closed.

Logout times: the gateway closes every session when it gets SIGINT / SIGTERM, so each one runs its disconnect hooks (logout time, friends' offline notice, online-time accounting) before the process ends, and at start it gives every role that was left online by a run that was killed or crashed (login time newer than logout time) a logout time of "now" (`Store.MarkStaleSessionsOffline`). Found on the device: friends showed a stale "last seen" for a role whose session was killed with the gateway.

LAN client (`tools/make_lan_client.py CLIENT_ROOT http://<LAN IP>:8081`, needs JDK 21 and a Homebrew LuaJIT): builds `dist/local-lan.apk` that works over Wi-Fi with no `adb reverse`, verified on the device (every request, the game TCP connection included, came from the phone's Wi-Fi address). It rewrites the host of every http URL in Java (`LanRewrite`), points the native url_config download at the server in `config.lua`, and puts the server's address on the native library's connection white list: `SmartSocket::ConnectAsyn` silently refuses any host that is not on `Data::getWhiteList()` (the three host strings of AppDelegate), which is why the loopback-only client could never reach a LAN address. Use `login_http.public_base` and the server row's host with the LAN address (`configs/lan.yaml`). It needs a small `--overlay` option in `reconstructed-client/build.py`; the baseline project is not touched.

Device session 2026-10-19 (`testdata/captures/device-session-2026-10-19/`): login, create role, mail claim, backpack, selling, daily sign-in, friend request and world chat all worked on the real client; see its NOTES.md, which also records that the patched client only works with loopback addresses (`public_base` and the server host 127.0.0.1 plus `adb reverse`).

WebSocket transport (for WeChat / Douyin mini-games, which cannot open raw TCP): set `gateway.ws_addr` and the gateway also serves `/ws`. It carries exactly the TCP byte protocol: binary messages are read as one byte stream (a frame may span messages, a message may hold several frames), the 23-byte handshake is optional, and sessions, signatures, pushes, kicks and the online table are shared with TCP (logging in on one transport kicks the other). Text messages and messages over 64 KiB (`MaxMessage`) close the connection. Requests without an `Origin` header (native and mini-game clients) are accepted; browser origins must match `gateway.ws_origins`. Mini-games require `wss://`: set `ws_tls_cert`/`ws_tls_key` or terminate TLS on a proxy. Verified by `internal/game/ws_test.go` (including a mutation check of the size limit) and by `tools/ws_smoke.mjs` against real processes (`node tools/ws_smoke.mjs <login base> ws://127.0.0.1:8802/ws`). Not yet tested with a real mini-game client.
